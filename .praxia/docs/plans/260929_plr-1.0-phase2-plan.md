## 1. Goal and non-goals

**Goal.** Move praxis off the parts of PLR 1.0's resource surface that are deprecated, so a
later upstream beta that deletes the aliases breaks nothing. Migrate stored class paths
(FQNs) to their 1.0 homes, then settle the `get_class_from_fqn` fallback. Along the way,
fix the two 1.0 regressions this recon found (visualizer rails, browser FQN resolution) and
shrink the web-repl wheel.

**Non-goals.**
- Phase 3, the modern device APIs (`prep.pipettes.*`, `pylabrobot.hamilton.star.*`). The
  legacy `LiquidHandler` stays, and so do the legacy `TipTracker` semantics on channels.
  `plate_staging.py` reads `liquid_handler.head96[*].has_tip`, which is legacy LH API and
  stays as it is.
- Re-assembling training data. No PR may change the bytes of a corpus, the eval pin or the
  golden set (see §7).
- Renaming praxis's own "rails" vocabulary in the Angular client (`railPosition`,
  `numRails`, `DeckRail`). This is praxis domain naming, not PLR API (open decision D6).
- The 91 FQNs that were already unresolvable at 0.2.2 (see §3.4). They are hygiene debt and
  not a 1.0 regression, so they get their own backlog item.

## 2. How upstream signals deprecation, and the replacements (recon a)

**Mechanism [V].** Upstream uses only the plain stdlib idiom
`warnings.warn(msg, DeprecationWarning, stacklevel=2)` inside the deprecated callable. There
are no decorators. This matches the note in `scripts/survey_plr_deprecations.py:9-12`.
`upstream_deprecations.tsv` has 95 sites in `pylabrobot/resources`: 91 warn at runtime and 4
are deprecated only in their docstring. Two consequences:
- A factory alias warns when it is **called**, not when it is imported. An import-time probe
  under `simplefilter("error")` therefore misses every factory alias. The probe here calls
  each one.
- The 4 docstring-only sites never warn: `TipSpot.tracker`, `get_tip`, `has_tip` and `empty`
  (`resources/tip_rack.py:205-226`, block comment `:199-201` "TODO: Remove in v1"). Only an
  AST scan finds them.

**CHANGELOG [V]** (`external/pylabrobot/CHANGELOG.md`, "Unreleased / Changed"): "`num_tracks`
replaces `num_rails` and `track=` replaces `rails=`; the old names are deprecated but keep
working, as do decks saved with `num_rails`. A STAR deck counts two fewer tracks than it
counted rails (STARlet 30, STAR 54) at the same positions." At 0.2.2 the counts were
`STARLET_NUM_RAILS = 32` and `STAR_NUM_RAILS = 56` (`dd79c4c89:resources/hamilton/hamilton_decks.py:21,26`).
The CHANGELOG says nothing about the factory aliases. Their only signal is the warning text.

**Replacements for the items praxis uses.** Each one was called side by side with its
replacement using the same `name`, and the two `serialize()` outputs were compared
(`probe_A.json`). All are **byte-equal**, including `model`, and only the old name warns [V]:

**`rails=N` vs `track=N` [V] (`probe_B.json`).** On STARLet and STAR, every N in
{1,3,8,9,15,21,25,30} gives the **same location**, and only `rails=` warns. The difference is
the bounds. `rails=` keeps the old STAR limits (`beyond = _rails_beyond_tracks = 2`,
`hamilton_decks.py:582`, `star_decks.py:26`):
- STARLet `rails=31/32` places; `track=31/32` raises `ValueError: Track must be between -4 and 30` (`:585`).
- The right-edge fit test allows `num_tracks + 1 + beyond` (`:614-621`). A resource that
  overhangs the right edge by up to 2 tracks (45 mm) fits with `rails=` and is **rejected**
  with `track=`. [V by source reading; not exercised by the probe]

**"Removed in v1b1" [V].** The Corning aliases say "will be removed in v1b1" (`corning/plates.py:183`),
yet 1.0.0b1 still ships them. They can disappear at any later bump, and that is the real
deadline for this phase.

**Serialized-deck compatibility [V].** Upstream's one explicit incompatibility is the
OT-2 deck (`resources/opentrons/deck.py:137-142`): "A deck serialized before slots became
resource holders stores labware as direct children and will not load." I could not find
general "serialized decks are incompatible" wording in the upstream docs or CHANGELOG
(searched `docs/`, `README.md`, `CHANGELOG.md`). Measured on 0.2.2-era artifacts:
`probe_old.json` deserializes **134/135** trees under 1.0. The one failure is exactly that
OT-2 deck (in `resource_definitions.plr_definition_details_json`). The old STARLet viz
fixture loads, with `num_rails`/`with_teaching_rack` deprecation warnings.

**Schema/migration mechanism [V].** Startup runs `Base.metadata.create_all`
(`praxis/backend/utils/db.py:252-268`, called from `main.py:128-130`). Alembic exists
(`alembic.ini`, `alembic/env.py`, a single baseline `alembic/versions/8bb1b518a5ae_v0_1_alpha_baseline.py`)
and is the documented upgrade path (`docs/index.md:111`, `.praxia/docs/reference/260121_alembic-migration-guide.md`),
but nothing runs it automatically. Discovery upserts catalog rows **by fqn** and never deletes
stale rows (`services/machine_type_definition.py:121,154`, `resource_type_definition.py:235`).
After a 1.0 discovery run, a pre-1.0 server DB therefore holds **both** the old-FQN rows,
which instances still reference by FK, and new legacy-FQN rows [R from code].

**Consumers of stored FQNs [V].**
`workcell_runtime/machine_manager.py:149,153,158,179` (backend, frontend, machine and deck
FQNs) and `resource_manager.py:97` all go through `get_class_from_fqn`
(`workcell_runtime/utils.py:52-72`, fallback `:21-49`). In the browser,
`web_bridge._import_class` (`:174-194`, which falls back to a top-level `pylabrobot.resources`
**name** and has **no legacy fallback**) and `web_bridge.create_configured_backend`
(`:1249-1262`, plain `importlib`, **no fallback at all**, and returns `None` on failure). Also
TS code generation from `definition.fqn` (`execution.service.ts:343-415`).

**praxis.db (browser seed) [V, `probe_D.json`].** It is generated by
`scripts/generate_browser_db.py` through LibCST static analysis. `accession_id` is
`md5(fqn)` (`:42-46`), so ids are **derived from FQNs**. Current contents: 201
`resource_definitions`, of which **51 are deprecated aliases** (the static parser also
catalogs the alias functions), 60 backends (4 are fictitious `pylabrobot.backends.simulated.*`
rows from `ensure_minimal_backends` `:830`), 19 frontends (1 fictitious `pylabrobot.scara.SCARA`),
12 decks, and 0 instances. Everything else resolves cleanly at 1.0.

**Browser persistence [V].** `sqlite-opfs.service.ts` loads `assets/db/praxis.db` into OPFS
**once**. It re-imports only on an empty DB or on a `PRAGMA user_version` mismatch, and a
mismatch **auto-resets and wipes user data** (`:215-221`). `CURRENT_SCHEMA_VERSION = 1`
(`workers/sqlite-opfs.types.ts:76`) has not changed since before phase 1. **A browser that
opened praxis before phase 1 still holds the 0.2.2 catalog.** In `probe_old.json`, the 0.2.2
praxis.db has 44/54 backend FQNs, 16/17 frontend FQNs and 16/16 machine-definition FQNs that
resolve **only** through the legacy twin. The browser path has no such fallback, so for those
users `create_configured_backend` returns `None` [R: consequence inferred from code plus
probe; not reproduced in a browser].

**What breaks if the server-side fallback were removed today** (on a DB populated at 0.2.2;
proxy = the 0.2.2 praxis.db, `probe_old.json`) [V]: 62 distinct FQNs (44 backend rows,
16 frontend, 16 machine-definition, 44 `compatible_backends` entries, 2 resource definitions).

The fallback does **not** cover deprecated factory aliases (50 rows there). Those still resolve
through upstream's aliases until upstream deletes them.

**Live server DBs.** None are reachable from here. Whether any Postgres instance with instance

## 6. The DB migration in detail (PR-7a)

**Scope of rewrite.** The columns in §3.2 that hold PLR FQNs: the `fqn` columns, JSON lists
(`machine_definitions.compatible_backends`, `deck_position_definitions.compatible_resource_fqns`),
and `machines.simulation_backend_name`. Serialized trees (`plr_definition`, `plr_state`,
`plr_definition_details_json`) are **not** rewritten. They carry class **names**
(`"type": "HamiltonSTARDeck"`) and `model` strings, not FQNs, and `model` is unchanged by the
factory renames [V, probe_A].

**Forward migration.**
1. **Backup.** Postgres: `pg_dump -Fc "$DATABASE_URL" > backup_pre_plr10_fqn_<ts>.dump`.
   SQLite: file copy plus sha256. Refuse to run if the backup step did not produce a non-empty
   file.
2. **Dry run (default mode):** `uv run --no-sync python scripts/plr10/migrate_fqns.py --database-url ... --dry-run --out <report.json>`.
   It reports, per table.column and map kind, the rows that would change, the catalog merges
   (below), `removed`-kind hits, FQNs not in the map that do not resolve, and instance rows
   whose deck placement would break under `track=` (a carrier at > `num_tracks` on a STAR deck).
   It writes nothing. The dry-run numbers are a finding, so they are pre-registered (§8).
3. **Apply,** chunked per table, then in batches of ≤ 500 rows, each batch in its own
   transaction. Every changed cell is written to a new table `plr_fqn_migration_log`
   (`table, pk, column, old_value, new_value, map_sha, batch_id, applied_at`) **in the same
   transaction**. A crash leaves a consistent prefix, and a re-run skips logged
   `(table, pk, column, map_sha)` rows. Each batch has its own statement timeout.
4. **Catalog merges.** The unique `fqn` columns (`resource_definitions`,
   `machine_backend_definitions`, `deck_definition_catalog`, plus `machine_definitions` and
   `machine_frontend_definitions`, which are unique in the model) may already hold the new FQN,
   because discovery inserted it. In that case: repoint every FK (`resources.resource_definition_accession_id`,
   `decks.resource_definition_accession_id`, `machines.*_definition_accession_id`,
   `resource_definitions.deck_definition_accession_id`, `decks.deck_type_id`, `machines.deck_child_definition_accession_id`,
   `deck_position_definitions.deck_type_id`) from the old row to the new row. Then **soft-retire**
   the old row: rename its fqn to `retired:<old_fqn>` and store the full row JSON in the log.
   Do not delete it. Otherwise rewrite the fqn in place.
5. Stamp alembic (`alembic_version`) at the new revision. DBs created by `create_all` have no
   `alembic_version`, so the runbook must say `alembic stamp 8bb1b518a5ae` first, after
   checking the schema matches the baseline [R: whether the baseline matches today's
   `create_all` schema is not verified. Check with `alembic check`/autogenerate diff in the PR].

**Idempotency.** Every write is `WHERE col = :old AND NOT EXISTS (log row for this map_sha)`.
A second run with the same map sha is a no-op, and the test asserts zero rows changed. A run
with a newer map (a new pin) applies only the delta.

**Reversibility.** `downgrade()` replays `plr_fqn_migration_log` for its `map_sha` in reverse
batch order: restore `old_value` and un-retire merged rows from their stored JSON. It restores
exactly what the upgrade changed and nothing else. If the log is missing, the fallback is the
`pg_dump` restore.

**Rows written by older clients after the migration.** Stale browsers, old server builds and
external manifests can re-insert pre-1.0 FQNs. Handling:
(a) read side: `get_class_from_fqn` and the browser normalizer keep resolving through the map
and the legacy twin (D1);
(b) write side: normalize FQNs through the same map in the definition/asset upsert services, so
new writes are canonical;
(c) the migration is idempotent, so re-running it (from a startup hook behind a flag, or by hand)
sweeps stragglers;
(d) the PR-9 counter shows whether any are still arriving.

**Decision on the fallback (D1), recommendation.** Keep it, but reshape it: map-driven, logged
once per FQN, counted. Remove it only when all of these hold: the upstream shims/aliases are gone
at a newer pin, the migration has run on every known server DB (D8: none hold data that matters,
so this condition reduces to "the dev/fixture DBs are migrated"), PR-7b has been live for one
release, **and** the counter reads zero over an agreed window. Removing it now would break 62
distinct FQNs on any un-migrated DB (§3.2), in exchange for deleting 20 lines.

file, and not as one wrapper. The builders run once each. The migration is resumable by design
(§6 step 3). The inventory scanner should write one JSONL shard per root dir with a sha256
