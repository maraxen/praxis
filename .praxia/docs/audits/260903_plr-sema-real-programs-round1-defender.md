## Per-objection verdicts

### O1 — BLOCKER as filed — **CONCEDED, but resolvable in-document (design paragraph + revised AC), not a recon gap**

**Challenger's claim, verified against code.** `training/verify/dispatcher.py:92`, `plan_call(call: Mapping[str, Any], index: int, setup, *, strict: bool) -> PlanResult`, is structurally a pure function of a JSON `call` dict and its **list index**. Its only call site is `training/verify/verifier.py:51`, inside `_execute`'s `for i, call in enumerate(call_sequence):` loop. `oracle_common.py`'s existing recorder, `recording_plan_call` (`plr-sema/eval/oracle_common.py:144-153`), works by monkey-patching the **module-level** `verifier.plan_call` name — which is only ever reached from inside that same `call_sequence` loop. I confirmed all three of these facts by reading the code directly, not by trusting either document.

§12.4.2's own text is exactly as self-contradictory as O1 states: "the fixture source is executed directly... **not replayed as a call sequence**" (line 619) immediately followed by "the per-iteration record comes from the same `plan_call` wrapper" (line 620-621). If a fixture is `await protocol_fixture_fn(lh, tip_racks, plate)` with a real Python `for` calling `lh.pick_up_tips(...)` directly, there is no `call_sequence`, no `index`, and `plan_call` is never invoked. This is a genuine, unrebuttable defect in the normative text — I could not find any other producer for the `(operation, iteration)` key on the executed side, and none is cited elsewhere in the document.

**Why this is a concession, not a "no oracle exists yet" recon block.** The task brief hypothesized a concrete alternative: instance-level monkeypatching of the bound `LiquidHandler` methods, with a call-site visit counter keyed by source line, correlated back to the graph operation via a recorded line number. I verified the two facts that make this mechanism viable, not merely plausible:

1. `OperationNode.line_number: int` **exists** (`models.py:532`, "Source line number") and is already populated by the extractor at every call site (`computation_graph_extractor.py:503`, `line_number=self._current_line`) and threaded through to `lower_graph`'s sideband (`ir.py:538`, `body_span[pc] = op.get("line_number", 0)`).
2. §12.4.2's static side already runs the **same fixture source** through the extractor a second time ("The static side runs the same source through §12.4.1's runner, `lower_graph`, and `check_ir`") — so the executed side's call-site line number and the static side's `OperationNode.line_number` are two readings of the identical source file, guaranteed to agree.

So a sound, minimal producer is: wrap each tool method on `setup.machine` (the same instance `build_setup` returns) with an async `functools.wraps` shim that reads its caller's line via `sys._getframe(1).f_lineno` (or `inspect.currentframe().f_back.f_lineno`), keeps a `dict[(method_name, lineno), int]` monotonic visit counter, and records `(method_name, lineno, visit_index)` per raise/call — independent of `plan_call`/`dispatcher.py` entirely. The correlation to the graph's operation id is then a lookup by `(method_name, line_number)` against `lower_graph`'s `sideband["span"]`/`origin`, which the increment's own T21 fixtures control by construction (single loop depth, one call site per method per fixture body, per the AC-12.17 "each with both tip outcomes" authored-fixture design).

**Minimal fix.** Replace §12.4.2's "Execution mechanics" paragraph (lines 618-621) with a normative paragraph naming this mechanism explicitly (instance-scoped method wrapping, not `plan_call`), and correct every downstream reference that assumes `plan_call`-reuse: AC-12.17's producer citation, and T21's task-row description (§12.8, T21 row) which currently doesn't name a recorder at all. This does **not** require resizing T21's ~460 LOC estimate materially — the replacement mechanism (a wrapper + a counter dict + a line-number join) is smaller than reusing and extending `plan_call`'s dispatch-table machinery would have been — but the estimate note should be revised to reflect the actual mechanism rather than silently keeping a number that was sized against the wrong plan. **This is a text-only + one revised AC fix, not a `needs_recon` gap**: the mechanism, its data dependencies, and its correctness argument are all fully available in the code already read.

### O2 — BLOCKER as filed — **CONCEDED, remedy (a) recommended**

**Verified.** §12.2.3 (lines 338-342) states a `trip=0` loop "contributes zero findings and no state change" under `min(0, K) = 0` visits. `test_wire_fuzz.py:153-167`'s `test_totality_findings_cover_all_operations` asserts `len(report.findings) >= len(graph_payload["operations"])` over **all** operations, unfiltered by `node_type`, and `test_check_graph.py:103-124`'s `test_operation_ids_are_a_subset_of_real_graph_ids` asserts exact set equality between `{f.operation_id}` and `{op["id"] for op in graph_payload["operations"]}`. Neither existing test excludes anything by `node_type`, confirming these are the literal ACs §12.3.4/AC-12.13 amend. §12.3.4's own amendment text reads `{op.id for op in graph.operations if op.node_type is not GraphNodeType.REGION}` — this excludes `REGION` headers, but **not** call-bearing body operations of a proved-trip-0 region, which are ordinary non-REGION `OperationNode`s. The challenger's counterexample (`range(0)` containing `pick_up_tips`) is exact: lowering produces `LOOP(trip=0)`, `CALL pick_up_tips`, `END`; walking visits `min(0,8)=0` times, so the `CALL`'s pc is **never reached** by `check_ir`'s pc loop (confirmed by reading `check_ir`, `plr-sema/src/plr_sema/check/__init__.py:427` — the loop only iterates `enumerate(bytecode.instructions)`; L1's "min(n,K) visits" is a semantic instruction to the *walk*, and a 0-visit region body's `CALL` pc still exists in the *stream* at a fixed pc, but nothing evaluates it there). The `pick_up_tips` op's id is a member of the "call-bearing" set (`node_type is not REGION`) but never appears in `{f.operation_id}` — AC-6.4(amended) fails on the document's own AC-12.6 fixture. This is a real, in-document contradiction, not a misreading by the challenger.

**Remedy choice.** I recommend **(a) — except proved-trip-0 region bodies from the call-bearing totality/equality set** — over **(b) — a totality-only dry visit**, for three reasons grounded in the spec's own stated positions:
1. §12.2.3 explicitly frames `trip=0` as "the one place a proved trip count *removes* obligations rather than adding them" (line 341-342) — a dry visit that manufactures a finding anyway directly negates that framing and reintroduces exactly the "widen-then-guess" pattern L1's `detail`-iteration-index design (§12.3.4 item 2) was built to make unsatisfiable.
2. A dry visit needs its own new rule for *what state* to visit against (`TOP`? the pre-region state?) and *what finding* to emit (a real `channel_state_unknown`, which then pollutes AC-12.14(iii)'s "every `SAFE` has an evaluated guard" invariant with a manufactured, never-executed one) — remedy (b) is a new design decision, not a bookkeeping fix.
3. Remedy (a) is a pure set-definition edit with no runtime-behavior change: the walk still does nothing for a trip-0 body, exactly as specified; only the *comparison sets* AC-6.4/AC-7.2/AC-12.13 check against change.

**Minimal fix.** Amend §12.3.4's AC-6.4 re-read and AC-12.13's totality clause to read over the call-bearing operations that are not nested inside a region whose proved trip is 0 (stated precisely), and add one sentence to AC-12.6 stating explicitly that the seventh (`range(0)`) fixture's body op is excluded from AC-6.4/AC-7.2/AC-12.13's target set by this carve-out, not merely "contributes zero findings." Text-only; no new fixture required since AC-12.6 already contains the trip-0 case — it only needs the totality assertion corrected.

### O3 — MAJOR as filed — **CONCEDED**

**Verified.** `check/__init__.py:462-478` exists exactly as the challenger describes: `if pc + 1 < n_instr and isinstance(bytecode.instructions[pc + 1], (ir.Loop, ir.Branch)): walk.widen(instr.receiver)`, with a docstring (464-476) that states its justification is `lower_graph`'s **old** convention where the region-owning operation "carries" its own `foreach_source`/`condition_expr` and is therefore always immediately followed by the region it opens. §12.2.2 (lines 280-307) explicitly replaces that convention: real region headers are now separate `CALL`-less `OperationNode`s. Under the new shape, "a `CALL` immediately followed by a `LOOP`/`BRANCH`" is true whenever a loop/branch simply follows an unrelated call in program order — the common case the challenger names (`lh.setup()` directly before a `for`).

I traced the challenger's AC-12.10 masking claim independently: E6's reset (§12.1.4) unconditionally overwrites `ChannelState` for the receiver after `setup()`'s own guards, so a stray pre-widen on `setup()`'s receiver is invisible in that specific fixture — but nothing in the spec generalizes this masking, and no named AC (12.10-12.14) puts an *ordinary* tip-relevant call directly before a region it doesn't own. This is a real latent defect: it would ship silently, degrading precision on any real protocol whose loop is preceded by (say) an `aspirate` rather than a `setup()`.

**Does T20 already imply removal?** No. T20's task row (§12.8) names "L1 bounded unroll... L3 restricting the blanket entry-widen to synthetic regions... B1 arm-wise branch walk... iteration index into `Finding.detail`; AC-11.7's bijection clause and main spec AC-6.4 amended" — none of this references `check/__init__.py:462-478` or its docstring's justification. L3's normative text (§12.3.3) only cross-references the **entry-widen** at `check/__init__.py:444-461`, a different code block from the compensation at 462-478. A fixer implementing L1/L2/L3 literally as specified could leave 462-478 untouched and ship the silent mis-widen the challenger describes.

**Minimal fix.** One sentence in T20's task row (§12.8) plus one clause in §12.3.3's L3: "L3 additionally removes the stale increment-2 compensation at `check/__init__.py:462-478`, which assumed the pre-§12.2.2 shape where a region-owning call carries its own region fields; under real headers this predicate no longer identifies the region's owner and must not fire." Plus one named fixture (as the challenger requests): an ordinary tip-state call immediately preceding an unrelated region it does not own, asserting that call's own guard evaluates against its real pre-call state. This can be folded into T20's existing fixture set rather than requiring a new task.

### O4 — MAJOR as filed — **PARTIAL: first half conceded (scoping/estimate gap), second half rebutted to "named follow-up, correctly out of scope"**

### O5 — MINOR as filed — **PARTIAL: not blocking, one paragraph owed, recommend keeping REGION distinct**

### O7 (orchestrator addendum) — proposed MAJOR — **CONCEDED for `continue`; PARTIAL for `break`/`return`/`raise`**

**The extractor does not model early exit at all.** Confirmed by reading `computation_graph_extractor.py:376-517`: there is no visitor for `Break`/`Continue`/`Return`/`Raise` anywhere, and `visit_Call` appends every machine call it sees to the enclosing region's body list unconditionally, in program order. §12.2.4 (lines 344-357) never mentions `break`/`continue`/`return`/`raise`.

**`continue` — genuine, unrebutted soundness gap.** A-COMPLETES's literal text (`260902_plr-sema-tip-typestate-increment.md:751-752`): "each operation preceding the one being checked completed **without raising**." This is exclusively about exceptions. A `continue` does not raise; it causes the rest of the current iteration's listed body ops to not execute while the loop legitimately continues to a genuinely reached next iteration. L1's threaded-state semantics always evaluates every listed body op every iteration. A `continue` before a `drop_tips` means the threaded state entering the next, actually-reached iteration is wrong, which can produce a `WILL_FAIL`/`SAFE` claim at a point the execution genuinely visits, based on a state the execution never had. Not discharged by anything in the document.

**`break`/`return`/`raise` — partially different, but undocumented.** These terminate the remaining (phantom) iterations the same way a raise does — subsequent unrolled iterations become claims about a trace segment never reached. If tier 2b's recorder (once O1 is fixed) marks unvisited call sites as not-reached and the comparison exempts them as it already exempts post-raise operations (`oracle_common.compare`'s `not_reached`), then these are sound by the same mechanism generalised from "raised" to "not reached for any reason". But A-COMPLETES's own text is narrower than needed.

**Minimal fix (both halves in one place).** Extend §12.2.3's trip-proof rule with a fourth condition: the extractor sets `trip = null` whenever the loop body, at any nesting depth within it (not inside a nested function), contains a `Continue`. Add a normative sentence generalising A-COMPLETES (or a sibling assumption row) from "did not raise" to "did not exit early via `break`/`return`/`raise` prior to the pc being checked", and note that tier 2b's comparison must mark call sites made unreachable by `break`/`return`/`raise` as not-reached. Add one `None`-trip entry to AC-12.6 for a `continue`-containing loop. Design-paragraph-level, not a re-architecture.
