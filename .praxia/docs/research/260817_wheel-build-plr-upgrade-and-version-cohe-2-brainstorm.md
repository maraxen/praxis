# Brainstorm: Wheel build, PLR upgrade, and version coherence for the praxis JupyterLite REPL refocus: what mechanism makes version drift between the PLR submodule pin, the built browser wheel, the hardcoded TypeScript/Python filenames, and the jupyterlite piplite index structurally impossible; who builds the wheel and when (local dev vs CI vs committed artifact); what the three-Python policy should be (venv 3.14.6 / ty 3.12 / pyodide 3.13); and how to shape the PLR import surface so the next upstream reorg is localized.

## Problem Frame
FRAME CONFIRMED as stated above. Restating tightly so it is on the record:

FIXED: pin dd79c4c89 (0.2.2); GH Pages static, no headers/no server logic; wheel is py3-none-any; micropip is the only installer and everything ends in a URL string; `jupyter lite build` is mandatory (tracked tree cannot serve); product = savable notebooks + device comms + visualizer; deferred paths may break.

NEGOTIABLE: wheel ownership and build timing; where (if anywhere) the filename lives; whether the two Angular Pyodide runtimes are in scope at all; whether the three-Python spread needs any action; the shape of the PLR import surface.

DRIVING ASYMMETRY: every failure mode here is silent-continue, and that is ONE pathology with five faces, not five bugs. Candidates get judged on whether they convert silence to noise, not just on whether they prevent drift.

MUST ANSWER: (a) detector + location for five drift scenarios; (b) who builds, and can an offline fresh clone deploy; (c) which Python is authoritative for what, using the MEASURED 3.13.2; (d) the import-surface rule that survives the NEXT pin bump.

Proceed to divergence.

- [user] === AXIS 1: WHAT IS THE UNIT OF COHERENCE? ===

COSTS: a new fetch (one more 404 surface), a manifest that can itself become a second source of truth, and a `+local` PEP 440 segment whose tolerance across micropip/piplite/service-worker cache keys is UNTESTED. FORECLOSES: nothing much — it is the conservative option. COSTS: build complexity moves into jupyterlite addon mechanics I have not verified; larger critical-path download; `+local` version tolerance in piplite is the same untested risk as A and now load-bearing. ## Pre-mortem Record
**User:** PRE-MORTEM. Six months out, five failure stories. I deliberately avoided repeating the prior session's four (gate disabled / manifest as second truth / +local rejected / offline never finished) — those still apply and their mitigations are carried. These are failures specific to what THIS design added, and three of them changed the design.

FAILURE 1 (most likely) — THE DEV MODE BECAME THE REAL MODE. This is the steelman's first point coming true THROUGH its own mitigation. praxis_browser shipped with a dev escape: a URL param or a localStorage flag that makes the bootstrap fetch the loose .py files from assets/shims/ instead of installing the wheel, so hardware debugging keeps its edit-reload loop. Because WebSerial/WebUSB work can only be validated against physical hardware, every developer used the dev path every day, and the wheel path was exercised only in CI. Within months the two diverged: a shim fix landed in the loose file and the wheel's copy of the same module was subtly different, or an import that worked under exec-into-namespace failed under normal module import. The wheel path was "green in CI" the whole time because CI tested the wheel and humans tested the files, and neither tested what the other tested. MITIGATION THE SPEC MUST CARRY: the dev mode must not be a SECOND CODE PATH. It must be `micropip.install` of a locally rebuilt wheel via a watch task (`just browser-wheels --watch`), so the dev loop is "rebuild the same artifact faster," never "load the source a different way." If that loop cannot be made fast enough to be tolerable, the spec should say so and the two-wheel decision genuinely deserves re-litigating — this is the winner's single most fragile assumption.

FAILURE 2 — WE INVENTED A NEW DRIFT AXIS WHILE CLOSING AN OLD ONE. Two wheels means a pair that can disagree: praxis_browser built from praxis sha X assumes a pylabrobot API from sha Y. The manifest faithfully records both shas and nothing compares them, because the design assumed "one recipe builds both, so they are born coherent." Then someone rebuilt only one — a partial `just` invocation, an incremental CI cache hit, a developer regenerating one wheel while debugging — and shipped a praxis_browser whose io-patching code targeted module attributes that had moved. Every check passed: both wheels present, both shas recorded, both installed, pylabrobot's own SHA matched its manifest entry. MITIGATION, and it is cheap: stamp ONE BUILD_ID (uuid or timestamp+shas hash) into BOTH wheels' _praxis_build_info in the same invocation, and make boot assert BUILD_ID equality across the two. That is strictly better than cross-referencing shas because it fails on partial rebuilds, which is the actual mechanism. Adopt into part 2.

FAILURE 3 — THE DELETION CAME BACK WRONG. Part 5 deletes _MACHINE_CLASS_MAP and create_machine_frontend. Six months later someone reviving the experimental extension needed machine instantiation, found it in git history, and copy-pasted it back — complete with `("pylabrobot.incubator", "Incubator")`, the exact entry the 0.2.2 bump broke, because the fix and the deletion were in the same commit and the resurrection came from the commit BEFORE it. MITIGATION, and this is also a correction to my own decision: the product direction says the experimental scope is KEPT ALIVE, NOT DELETED. Straight deletion is in tension with that. The right move is MOVE, not DELETE — relocate _MACHINE_CLASS_MAP and create_machine_frontend into the experimental extension's own tree in the same commit, WITH the Incubator fix applied and with the symbol contract covering it. Then the revival path is "use the thing that is sitting there" rather than "resurrect from history," and the reorg exposure is still out of the REPL payload. Same benefit, no resurrection hazard. Amend part 5.

FAILURE 4 — THE SYMBOL CONTRACT ROTTED INTO DECORATION. It is a hand-maintained data file, and the conformance test only checks what is listed. Someone added a new pylabrobot import to praxis_browser and did not add a contract entry. The test stayed green — it is structurally incapable of failing on an unlisted import — and coverage decayed silently until the next reorg broke something the contract had never heard of. This is the same pathology as everything else in this area: a check that cannot fail is indistinguishable from no check. MITIGATION: the contract must not be purely hand-maintained. Add a test that AST-scans the browser subtree (and the shipped notebook templates) for every `pylabrobot.*` import and asserts the contract is a SUPERSET of what it finds. Hand-maintain the expectations; machine-maintain the coverage.

FAILURE 5 — THE PYTHON POLICY EXPIRED UNNOTICED. Part 6's revision trigger is "jupyterlite-pyodide-kernel ships a release whose pyodide is on 3.14." Nobody watches for that. A routine dependency bump moved jupyterlite-core, which moved the pyodide-kernel, which moved the in-browser CPython from 3.13 to 3.14 — and the policy that said "pin the kernel, derive the Python" worked exactly as designed, silently, which is the problem. Code authored against 3.13 either broke in a way blamed on something else, or subtly changed behaviour. MITIGATION that converts the policy from a document into an enforced invariant: the boot ledger must RECORD the observed sys.version_info and pyodide version, and the CI smoke must ASSERT them against a declared expected value in the repo. Then a kernel bump that moves the Python fails CI loudly and forces an explicit decision, instead of shipping. This also gives part 6 a detector, which it currently lacks — every other part of the winner has one.

Net: three amendments (BUILD_ID equality; move-don't-delete; AST-superset contract test), one new required detector (declared-vs-observed in-browser Python asserted in CI), and one honestly-flagged fragility (the dev loop) that is the winner's most likely undoing.
