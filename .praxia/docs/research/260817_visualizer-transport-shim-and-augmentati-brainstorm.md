# Brainstorm: Visualizer transport shim and augmentation API for the praxis JupyterLite REPL refocus: how to drive the PyLabRobot Konva visualizer from an in-browser Pyodide kernel with no websocket server, and what shape the augmentation API should take, given proven-by-execution spike results (renderer is a pure function of injected JSON; 4 vis.js spans are the entire network coupling; a second Konva overlay layer attaches with zero lib.js edits).

## Problem Frame
FIXED (cannot change):
- F1. The renderer stays a vendored third-party artifact. lib.js is 5867 lines of Konva code we do not own, do not understand in detail, and will re-vendor from upstream repeatedly. Zero edits to it. Non-negotiable.
- F2. No websocket server, no localhost:2121/:1337. Everything runs in the browser. The Python side is a Pyodide kernel in a Web Worker; the renderer is DOM-side. They are separated by a worker boundary (structured clone), not a socket.
- F3. The page must be servable as static files. No server-side rendering, no build-time-only-in-Angular tricks. GH Pages is the deploy target.
- F4. PLR's asyncio callback plumbing (visualizer.py:140-151, :628-682) cannot be used as-is — self.loop.call_soon_threadsafe blows up without a running loop (proven: spot.tracker.commit() -> 'Event loop has not been started.').
- F5. The wire format (STANDARD_FORM_JSON_VERSION 0.1.0, the {event, id, data} envelope, set_root_resource/resource_assigned/resource_unassigned/set_state) is upstream's, not ours. We consume it; we do not get to redesign it.

NEGOTIABLE:
- N1. Whether we vendor the PINNED submodule's visualizer JS or UPSTREAM master's. Spike says upstream is strictly better (gridLayer, visibility toggles, method_registry cutting 461KB -> 118KB) and is backward-compatible with an un-bumped 0.1.6 kernel via lib.js:967-968's `resourceData.methods || methodRegistry[resourceData.type]` precedence.
- N2. Whether the Python side uses PLR's Visualizer class at all, or bypasses it and calls the pure serializers directly (_serialize_with_methods, _sanitize_floats, _assemble_command — proven callable with no server).
- N3. Whether vis.js is patched, replaced wholesale, or shimmed from outside without touching the file.
- N4. Where the visualizer lives relative to the notebook: separate iframe, sibling pane, or embedded output cell.
- N5. Whether augmentations are Python-authored, JS-authored, or both.
- N6. How much of upstream's GIF/export UI we keep.

SHARPEST TENSION I want the divergence to attack: criterion A (drift resilience) and criterion D (augmentations survive lib.js INTERNAL refactors) pull in opposite directions from criterion E (small enough to ship). The cheapest augmentation seam is the one the spike proved — reach into lib.js's `resources[name].group` and `stage` globals — but that is precisely a dependency on lib.js INTERNALS, which is the thing criterion D says must not break us. I want at least one candidate that refuses that shortcut and pays a different price.

HIDDEN ASSUMPTION I want surfaced: everyone assumes the visualizer is a passive display. The user asked for "augmentations", which may imply INPUT — clicking a well to get a Python handle, dragging a plate to reposition it. If augmentations are bidirectional, the transport seam is not one-way and several otherwise-attractive designs die.

## Idea Pool
- [ai] T1 — DUCK-SOCKET INJECTION. Keep upstream's Visualizer class byte-intact and unsubclassed. Never call setup(). Instead assign two private attributes: viz._websocket = _BrowserSink() (an object whose only method is `async def send(self, s: str)`, forwarding to JS) and viz._loop = asyncio.get_event_loop() (pyodide's live WebLoop). Then call viz._send_resources_and_state() once, in place of the browser's "ready" handshake. Everything else — id generation, _sanitize_floats, _serialize_with_methods, the three resource callbacks, the set_state batching/flush, show_machine_tools — executes upstream's own code path unmodified. Drift surface = 3 private names (_websocket, _loop, _send_resources_and_state) and the duck-type contract `async send(str)`.

Uses the named, documented-ish method surface rather than private attributes. Drift surface = the signatures of setup/send_command/stop plus __init__'s constructor params (host, ws_port, fs_port, open_browser, name, favicon, show_machine_tools_at_start — already 7 and growing).
- [ai] T3 — OWN THE PUMP, BORROW ONLY THE PURE FUNCTIONS. Do not instantiate Visualizer at all. praxis/visualizer/pump.py imports only _serialize_with_methods and _sanitize_floats (pure, proven callable serverless) and re-implements ~120 lines: register_did_assign_resource_callback / register_did_unassign_resource_callback / register_state_update_callback against a SYNCHRONOUS sink, its own id counter, its own microtask-based batching. Zero asyncio. Drift surface moves OFF visualizer.py (where the 32 commits are) and ONTO Resource's callback API + the wire format. Cost: we own the pump and must manually track new event types upstream adds (show_machine_tools and method_registry were both added in the delta).
- [ai] T4 — JUPYTER-NATIVE TRANSPORT (comm / _repr_mimebundle_). Ship the visualizer as a notebook output: a PraxisVisualizer object whose _repr_mimebundle_ emits an iframe/srcdoc carrying vendored lib.js+konva, and whose message channel is Jupyter's own comm protocol (or an anywidget-style widget) rather than a bespoke postMessage bridge. Transport becomes "whatever JupyterLite already implements for kernel<->frontend messaging". Materially different in WHERE the seam lives: not our bridge, but the notebook protocol. Consequence: the visualizer lives in an output cell, is savable/serializable with the notebook, and multiple visualizers can coexist per notebook.
- [ai] T5 — WEBSOCKET POLYFILL (keep upstream 100% untouched, both sides). Install a fake `websockets` module into the Pyodide kernel and a fake `WebSocket` global in the visualizer document, both backed by postMessage. Then upstream's Visualizer.setup() and upstream's unmodified vis.js openSocket() both "work" verbatim — zero patches to vis.js, zero patches to visualizer.py, zero private-attribute access. Maximum drift immunity by construction: we impersonate the protocol boundary instead of bypassing it. Cost: must also fake http.server/threading/webbrowser for setup()'s _run_file_server, and impersonating `websockets.asyncio.server.serve` is a nontrivial API surface.
- [ai] A1 — OVERLAY LAYER (JS-side, draws on top). The spike-proven seam: stage.add(new Konva.Layer({name:'praxis-overlay'})), positioned via resources[name].group.getClientRect({relativeTo: stage}). Augmentations are JS functions receiving (overlayLayer, resources, stage). Requires the scaleY(-1) counter-flip for text. Depends on lib.js INTERNAL globals: `stage`, `resources`, and each entry having a `.group` Konva node.
- [ai] A2 — MESSAGE-BOUNDARY MIDDLEWARE (wire-format-only dependency). An interceptor chain wrapping the inbound envelope before it reaches processCentralEvent. Each augmentation is `(envelope, next) => ...` and may: rewrite the payload, consume a praxis:* synthetic event (MANDATORY — vis.js:112-113 throws on unknown events), or pass through. Depends ONLY on the {id, version, event, data} envelope and the 5 known event names — the wire format that held stable across a 222-commit delta (STANDARD_FORM_JSON_VERSION 0.1.0 on both sides). Zero dependency on lib.js internals. Cannot draw anything by itself.
- [ai] A3 — PYTHON-SIDE TREE ENRICHMENT (zero JS). Augmentations are Python decorators that rewrite the serialized dict before send — recolor a well by editing its state, inject a synthetic child Resource to act as a marker, annotate `methods`. Advantage: augmentation authors write Python, never touch JS, and everything is testable headlessly with no browser. Disadvantage: strictly limited to what lib.js ALREADY knows how to draw; you are programming the renderer through a keyhole, and injecting fake Resources pollutes the tree that the sidepanel/Workcell Tree also renders.
- [ai] A4 — SIDECAR CANVAS / SHADOW STAGE. Refuse to touch lib.js's stage at all. Mount a SECOND, fully independent Konva stage (or plain 2D canvas / absolutely-positioned DOM layer) in a sibling element stacked over the visualizer div, and keep it in sync by maintaining our OWN geometry model derived from the wire payload (every resource's location/size is in the set_root_resource JSON). Pays a real price — we must re-derive the world->screen transform and mirror pan/zoom ourselves — to buy total independence from lib.js internals. This is the candidate that refuses the internals shortcut.
- [ai] A5 — BIDIRECTIONAL / INPUT AUGMENTATIONS. Augmentations emit upward: overlay-layer or stage click handlers post {event:'praxis:pick', resource_name} back to the kernel, which resolves it to a live Python object and (e.g.) binds it to a variable, prints a repr, or triggers a protocol step. Turns the visualizer from a display into an input device. Forecloses any design where the transport is one-way; requires an inbound queue on the Python side and a story for "kernel is busy running a cell".

## Decision Log
- [REJECT] T5 — Websocket polyfill on both sides (impersonate the protocol boundary): False immunity. To let upstream's setup() run verbatim we must impersonate websockets.asyncio.server.serve as an async context manager, http.server.HTTPServer, threading.Thread and webbrowser.open — a LARGER and less stable surface than the 3 private names T1 touches, and one that is stdlib/third-party-version-sensitive rather than PLR-version-sensitive. It relocates coupling from a surface we can contract-test (PLR internals, one repo, one pinned SHA) to one we cannot (the websockets library's server API). Buys nothing the duck-socket does not already buy.
- [REJECT] V2 — NPM/ESM build pipeline for Konva: Couples the static-page build to the Node/Angular workspace we are explicitly decoupling from (product direction: Angular deferred to the experimental extension). Also a mechanical mismatch: lib.js expects a UMD global window.Konva, so an ESM bundle needs an extra shim. V1's hash-pinned fetch from raw.githubusercontent.com is proven to work in this environment (200, 158,587 bytes, sha256 verified) and produces a byte-equivalent artifact to what unpkg serves for konva@8. Fewer moving parts, no Node on the critical path.
- [REJECT] D3 — Shadow vis.js (rewrite rather than patch): Conceptually cleanest but fails silently in the one way we cannot afford. vis.js is 212 lines and looks like pure dispatch, but it carries at least two non-obvious behaviours: snapshotResource() MUST run before removeResource() so the machine-tool arm panel can replicate a destroyed resource (the file carries a comment saying exactly this), and the set_state branch calls updateSidepanelState() per resource to avoid a full tree rebuild. Rewriting means silently dropping features we do not use TODAY and will not notice losing. D2's anchor-asserted patch keeps upstream's semantics byte-for-byte outside the 4 replaced spans and converts drift into a loud build failure instead of a silent behaviour loss.
- [DEFER] A4 — Sidecar shadow canvas (independent second Konva stage, own geometry model): Not rejected on merit — it is the only candidate with genuinely zero dependence on lib.js internals, and it is the right escape hatch if PLR's renderer churn becomes intolerable. But it requires re-deriving the world->screen transform and mirroring pan/zoom, and the spike proved the CHEAP path works: an overlay layer added to lib.js's own stage stayed locked to resources through a 2.6x zoom with zero lib.js edits. A6's narrow adapter buys most of A4's resilience for ~5% of the code. Deferred with a named trigger: adopt A4 if the A6 adapter needs repair on more than two consecutive PLR bumps.
- [MERGE] T1 + T2 + T3 merged: duck-socket injection, plus a minimal subclass overriding ONLY the three asyncio-welded callbacks: Pure T1 rests on an unverified claim — that pyodide's WebLoop satisfies call_soon_threadsafe (visualizer.py:666), call_soon (:673), asyncio.run_coroutine_threadsafe (:650, :659) and ensure_future (:682). Faking the loop instead means impersonating asyncio internals (_chain_future, get_loop, add_done_callback), which is CPython-version-sensitive — worse than the disease. The merge dodges both: duck-type _websocket (T1's insight — the websocket property is only ever `self._websocket` and has_connection() is `is not None`, so any object with `async def send(str)` satisfies it), and use T2's subclass mechanism to override exactly the three methods the spike PROVED are non-reusable (_handle_state_update_callback, _handle_resource_assigned_callback, _handle_resource_unassigned_callback), replacing asyncio dispatch with a synchronous send. This adopts T3's synchronous-pump philosophy for the ~25 lines that need it, while _assemble_command, _serialize_with_methods, _sanitize_floats, _generate_id, send_command and _send_resources_and_state all still run upstream's unmodified code. Critically: every one of those callback sites calls send_command with wait_for_response=False, so the coroutine never truly suspends and a one-step drive-to-completion runner is sufficient — and a loud RuntimeError if it ever DOES suspend becomes a free drift detector.
- [ACCEPT] D4 (new, emergent) — Source-hash sentinel test over the shadowed upstream methods: Fills the gap the merge opens. Once we override three upstream methods, upstream can change what data dict resource_assigned carries and our override goes stale SILENTLY — the exact failure class (silent, partial) that the wheel-filename bug and the WebSerial `window` import already demonstrated in this codebase. Mitigation is cheap and needs no browser: a plain unit test asserting sha256(inspect.getsource(Visualizer._handle_resource_assigned_callback)) and its two siblings match recorded values, plus the three pure functions we import. Fails loudly on the exact methods we shadowed, on the exact bump that changes them, in CI, in milliseconds. Complements D2 (vis.js anchors, patch time) and D1 (golden render, render time) — three detectors covering three distinct drift surfaces: Python semantics, JS transport, JS renderer.
- [ACCEPT] A2 + A6 two-tier augmentation API (Tier 1 wire-format middleware; Tier 2 canvas access via one narrow adapter): Resolves the session's sharpest tension (drift resilience vs shippability) by layering rather than choosing. Tier 1 depends only on the {id, version, event, data} envelope and the 5 known event names — a surface demonstrably stable across a 222-commit delta (STANDARD_FORM_JSON_VERSION 0.1.0 on both pinned and upstream, and 0.1.6-generated payloads render unmodified on the upstream renderer). Tier 2 concentrates ALL lib.js-internals coupling (`stage`, `resources`, `.group`) into one ~40-line adapter file that is the only place in the repo permitted to name a lib.js global. This lets us make an honest, differentiated stability promise to augmentation authors instead of one vague one. A3 (Python tree enrichment) becomes a Tier-1 variant that happens to run kernel-side; A5 (bidirectional) becomes Tier 1's return channel rather than a separate concept.
- [ACCEPT] F3 (click-to-Python) as the FIRST augmentation, ahead of F1 (time-travel state-diff highlight): Chosen on risk retirement, not on demo value. F1 exercises only the downward path, which both spikes already proved works (injected JSON renders; set_state deltas repaint). F3 exercises the UPWARD path, which nothing has proved and which forecloses the most if discovered late — a one-way transport is materially cheaper and we would be tempted into it. ## Pre-mortem Record
**User:** PRE-MORTEM — six months on, it has definitively failed. Most likely stories, ordered by probability:

FAILURE 1 (most likely) — The tier boundary was never enforced, so it stopped existing. We shipped Tier 1 and Tier 2 as a documented distinction, but the lib-adapter is just a JS module and nothing PREVENTS an augmentation from writing `stage` or `resources` directly. The first time someone needed a geometry read the adapter did not expose, they reached past it, because that is a 1-line change and extending the adapter is a 20-line change plus a contract test. Six months later, eleven augmentations each touch lib.js internals directly, the adapter is vestigial, and a PLR bump breaks all eleven. The stability promise we made to authors was false, which is worse than never making it. PREVENTION: the boundary must be mechanically enforced, not documented — augmentations load in a scope where the lib.js globals are not reachable, plus a lint rule that fails CI on any reference to `stage`/`resources`/`.group` outside lib-adapter.js. If we cannot enforce it, we should not claim the two tiers exist.

FAILURE 2 — D4 became a rubber stamp. The source-hash sentinel went red on a whitespace change in month two. Someone bumped the hash without reading the diff, because that is what the failure mode of a hash sentinel is. In month five upstream changed the data dict for resource_assigned; the hash went red; someone bumped it again; resources silently stopped appearing when assigned after initial load. This is the runner-up's sharpest criticism and it is correct as stated. PREVENTION: D4 must not be a bare hash. It must print the actual diff against the recorded source and require the bumper to also re-record a captured ENVELOPE fixture from the new upstream — so bumping is not free, and the thing you re-record is the thing that actually matters (the wire payload), not the source text.

FAILURE 3 — The upward path (F3/A5) was under-designed at the kernel-busy boundary and poisoned the REPL. A click arrives while a cell is running. We queue it. The cell raises. The queue is now inconsistent with kernel state, or the click executes against a stale resource tree, or worst, we injected code into the REPL that the user did not type and cannot reproduce by re-running the notebook. The 'savable notebook' promise breaks: the notebook no longer reproduces its own outputs, because some of its state came from clicks. PREVENTION: F3 must never inject hidden state. It should write a real, visible, re-runnable line of code into the next cell — the click is a code-authoring convenience, not a side channel. Anything else and the notebook stops being a reproducible artifact, which is the whole product.

FAILURE 4 — D1 was disabled. The golden-render test needs unsandboxed headless Chromium and a pre-cached browser binary; the spike proved neither is available under the default sandbox and that Playwright's expected revision was not downloadable. Someone marked it allow-failure during a red CI day, and it stayed that way. Then lib.js drift landed silently. PREVENTION: if D1 cannot be made reliable in CI on day one, it is not a detector, and we must NOT count it as one of three — we would be shipping the winner's cost with two thirds of its safety.

FAILURE 5 (the one that kills the whole area, not just the design) — the assumption I flagged in the forcing beat turned out false in a way we did not catch. If pyodide's runtime cannot drive upstream's send_command coroutine to completion synchronously, or if a future upstream change makes those callback paths genuinely await, the whole 'reuse upstream's pump' premise collapses and we are doing T3 anyway, six months late. PREVENTION: spike it BEFORE the spec is trusted. Nothing in either executed spike drove the renderer from a live Pyodide-hosted Visualizer — each half was proven separately and the join was never tested.

None of these five change the winner. Three of them (1, 2, 4) change what the spec must REQUIRE, and I want those folded in as hard acceptance criteria rather than nice-to-haves. Failure 5 changes the sequencing: a join spike is a precondition, not a task.

## Acceptance Criteria
**Given** FIXED (cannot change):
- F1. The renderer stays a vendored third-party artifact. lib.js is 5867 lines of Konva code we do not own, do not understand in detail, and will re-vendor from upstream repeatedly. Zero edits to it. Non-negotiable.
- F2. No websocket server, no localhost:2121/:1337. Everything runs in the browser. The Python side is a Pyodide kernel in a Web Worker; the renderer is DOM-side. They are separated by a worker boundary (structured clone), not a socket.
- F3. The page must be servable as static files. No server-side rendering, no build-time-only-in-Angular tricks. GH Pages is the deploy target.
- F4. PLR's asyncio callback plumbing (visualizer.py:140-151, :628-682) cannot be used as-is — self.loop.call_soon_threadsafe blows up without a running loop (proven: spot.tracker.commit() -> 'Event loop has not been started.').
- F5. The wire format (STANDARD_FORM_JSON_VERSION 0.1.0, the {event, id, data} envelope, set_root_resource/resource_assigned/resource_unassigned/set_state) is upstream's, not ours. We consume it; we do not get to redesign it.

NEGOTIABLE:
- N1. Whether we vendor the PINNED submodule's visualizer JS or UPSTREAM master's. Spike says upstream is strictly better (gridLayer, visibility toggles, method_registry cutting 461KB -> 118KB) and is backward-compatible with an un-bumped 0.1.6 kernel via lib.js:967-968's `resourceData.methods || methodRegistry[resourceData.type]` precedence.
- N2. Whether the Python side uses PLR's Visualizer class at all, or bypasses it and calls the pure serializers directly (_serialize_with_methods, _sanitize_floats, _assemble_command — proven callable with no server).
- N3. Whether vis.js is patched, replaced wholesale, or shimmed from outside without touching the file.
- N4. Where the visualizer lives relative to the notebook: separate iframe, sibling pane, or embedded output cell.
- N5. Whether augmentations are Python-authored, JS-authored, or both.
- N6. How much of upstream's GIF/export UI we keep.
