# Brainstorm: Standalone web-repl extraction, shell, and notebook persistence for praxis REPL refocus (task_id 260817_praxis_repl_refocus): what is the right boundary for a standalone PyLabRobot JupyterLite artifact, what replaces the Angular shell (theme + device-auth user-gesture dialog + iframe host), how to make savable notebooks actually true, whether a build step is still needed, and what happens to Direct Control.

## Problem Frame
FIXED (cannot change):
- F1. Product: a static webpage serving a PLR JupyterLite notebook workspace. No server at runtime. Deployable to GitHub Pages.
- F2. Deferred surfaces (Angular SPA, catalog, protocol runner, backend, scheduler, keycloak, FastAPI) are KEPT ALIVE in-repo as an experimental extension, not deleted.
- F3. Browser platform laws: BroadcastChannel is same-origin-only. requestDevice() for WebUSB/WebHID requires a user gesture, and a Pyodide Web Worker cannot produce one — the gesture must originate in a document that has an open user-activation window. WebSerial/WebUSB permissions are granted per-ORIGIN, so an origin split also splits the permission grant store.
- F4. JupyterLite's browser storage identity is derived from baseUrl unless contentsStorageName is pinned (EXECUTED proof).
- F5. GH Pages serves no custom headers, so no COOP/COEP, so no SharedArrayBuffer.
- F6. The vendored assets/jupyterlite/ tree is non-bootable and mostly untracked. A build step exists whether we like it or not, unless we consciously replace it with a committed artifact.

NEGOTIABLE:
- N1. Directory boundary: new top-level web-repl/ vs staying under praxis/web-client/src/assets/ vs a separate repo vs a git-subtree/npm-package.
- N2. Whether Angular keeps embedding the REPL at all, and if so whether same-origin subpath or cross-origin.
- N3. Whether the shell is an iframe host at all, or whether JupyterLite becomes the top-level document.
- N4. Whether device-auth dialog lives in the host document, inside JupyterLite as an extension, or in the notebook page itself.
- N5. Persistence mechanism mix: IndexedDB only, + File System Access API, + OPFS, + explicit export/import, + persist() request, + autosave tuning.
- N6. Build: `jupyter lite build` in CI vs committed prebuilt tree vs hybrid (commit a release tarball).
- N7. Direct Control: retire to experimental / keep as-is / rebuild as a JupyterLite extension.

HIDDEN CONSTRAINTS I want on the record before diverging:
- H1. If the REPL becomes the top-level document rather than an iframe child, the gesture problem gets EASIER (no cross-frame permission delegation, no `allow=` attribute needed) but we lose the existing Angular dialog implementation and must rebuild it inside JupyterLite.
- H2. Any move of the served path orphans existing notebooks unless contentsStorageName is pinned FIRST, in the same release that moves the path. Ordering matters — this is a migration hazard, not just a config nit.
- H3. Air-gapped lab machines are plausibly in scope for a lab-automation product; the current build hard-depends on cdn.jsdelivr.net. That pressures "static webpage" toward "vendored Pyodide", which changes artifact size materially (~10MB+).
- H4. There is currently ZERO frontend CI test coverage, and the box has no node/npm. Any design whose correctness depends on untested browser glue is a design that will silently rot — same failure class as the already-dead vendored build.

Confirm this frame and let's diverge.

## Idea Pool
- [user] Five materially different full-stack approaches. They differ on the load-bearing axes (where the shell lives, what the repo boundary is, how the artifact is built, how the gesture chain is preserved, how persistence is made real) — not variations on one theme.
- [user] === A. PORT — thin vanilla host shell + iframe, in-repo, CI build ===
- [user] Transliterate the Angular glue into ~300 lines of vanilla TS. New top-level `web-repl/` holds index.html, host.ts, the jupyterlite config, shims, wheels, bootstrap. The iframe stays; BroadcastChannel stays same-origin; the 97a75988 dialog is reimplemented as a `<dialog>` element in the host. Theme stays a URL param. Angular's playground component is reduced to an iframe pointing at the SAME same-origin path, so the deferred surface keeps working unchanged.
- [user] === B. NATIVE — kill the shell; everything becomes a JupyterLab extension ===
- [user] Serve `lab/index.html` as the TOP-LEVEL document. No host page, no iframe, no BroadcastChannel. Four labextensions: praxis-device-auth (Lumino dialog + toolbar button, kernel talks to it over a Jupyter Comm), praxis-bootstrap (a proper kernel-start hook replacing the ?code= URL hack), praxis-fs (File System Access commands in the File menu), praxis-persist (calls storage.persist(), renders a status indicator in the status bar). Requires a node/npm labextension build.
- [user] === C. AUSTERE — zero custom JS; config + Python only ===
- [user] We write NO browser JS at all. The artifact is `jupyter lite build` output plus jupyterlite-config.json. Notebook surface = stock lab/. Device gesture is solved in Python: web_bridge renders an HTML button into cell output via IPython.display; its click handler is a main-thread JS callback that calls requestDevice() with live user activation. Saving to disk is `praxis.save_notebook()` → showSaveFilePicker(), also click-initiated. Nothing we own can rot because we own nothing.
- [user] === D. SPLIT — separate repository, separate origin ===
- [user] `praxis-repl` becomes its own repo with its own GH Pages origin and release cadence; praxis consumes it (or just links to it). Clean product boundary, independent versioning, own device-permission origin. Costs: BroadcastChannel breaks cross-origin (must become postMessage), two CIs, and this repo has demonstrated it does NOT keep submodules current (external/pylabrobot is 222 commits behind).
- [user] === E. KIOSK — installable offline-first PWA ===
- [user] Invert the deploy model. The REPL is a PWA: web app manifest, service worker precaching the entire build INCLUDING a vendored Pyodide (kills the jsdelivr hard dependency), install prompt. Directly attacks two problems at once: air-gapped lab machines get a genuinely offline artifact, and Chromium grants persistent storage automatically to installed apps — so storage.persist() stops being a coin flip. Costs: service-worker versioning is its own failure class, and a stale SW is the single worst debugging experience in web dev.
- [user] Plus these AXIS ideas that can graft onto any of the above:
- [user] F. Persistence: FSA "working folder" mode — user grants a real directory once, handle stored in IndexedDB, every save mirrors to disk. Key unlock: the product ALREADY requires Chromium for WebSerial/WebUSB, so File System Access API availability is a non-issue. The usual portability objection does not apply here.
- [user] G. Build: CI builds a versioned tarball published to GH Releases; deploy downloads it; devs `just repl-fetch` the same artifact. Nothing 70MB goes into git, and there is one reproducible byte-identical thing.
- [user] H. Loud-failure contract: praxis:ready is emitted ONLY after `import pylabrobot` succeeds; otherwise praxis:error with a visible banner. Wheel filename read from a generated manifest.json, never a literal.
- [user] I. Storage migration: pin contentsStorageName to a fixed literal ("praxis-repl") in the SAME release that moves the path, plus a one-time copy step from the old baseUrl-derived DB name.

## Decision Log
- [REJECT] C. AUSTERE — zero custom JS, device gesture solved in Python via IPython.display button: Disqualified on a realm boundary, not on taste. The JupyterLite Pyodide interpreter runs in a Web Worker; IPython.display output renders in the main-thread document. A main-thread DOM click handler cannot synchronously invoke a worker-resident Python proxy, so the bridge must be postMessage, which is async and discards user activation before requestDevice() is reached. This is precisely the constraint commit 97a75988 was written to solve. Zero-custom-JS is therefore incompatible with product requirement (b), real device comms. Salvaged sub-idea: its discipline — minimise owned browser code to the smallest surface that can carry user activation, and prefer config keys (contentsStorageName, --pyodide) over code everywhere else.
- [REJECT] D. SPLIT — separate praxis-repl repository on its own GitHub Pages origin: Rejected on three independent grounds. (1) A cross-origin split breaks BroadcastChannel, forcing a rewrite of the kernel-to-host protocol to postMessage for no product benefit — the spike observed the existing channel working, so this is pure destruction of a working seam. (2) WebSerial/WebUSB permission grants are per-origin, so an origin change silently invalidates every device permission a user has already granted, with no migration path. (3) The repo has demonstrated it does not keep cross-repo pins current: external/pylabrobot is pinned 222 commits and six months behind upstream. Adding a second such boundary predictably produces a second stale pin. Salvaged sub-idea: the PRODUCT boundary D wants is real and can be had inside one repo by making web-repl/ a top-level sibling with its own build, its own deploy job and no import path into praxis/.
- [DEFER] B. NATIVE — rebuild the shell as four federated JupyterLab labextensions: Architecturally the most correct end state — File-menu export, status-bar persistence indicator and a Comm-based device-auth dialog are all where a Jupyter user would look for them — but it is the wrong FIRST move. It requires a node/npm + webpack federated-extension toolchain that this machine does not have (bun only, no node_modules), commits us to the @jupyterlab/* extension API churn surface, and lands in a repo with literally zero frontend CI coverage. H4 says untested browser glue rots; a labextension build is the largest possible surface of exactly that. Deferred, not rejected: B' is deliberately designed so that praxis-shell.js can later be repackaged as a labextension without changing the kernel-side contract, because the contract is BroadcastChannel message shapes, not JS API surface.
- [REJECT] A. PORT — thin vanilla host shell hosting the REPL in an iframe: Runner-up, rejected once the iframe was shown to be non-load-bearing. BroadcastChannel spans a Worker and a same-origin top-level document, so the existing kernel-to-host protocol never needed the frame; the spike's own log shows the page receiving praxis:ready. With that corrected, A's iframe is cost paid purely on behalf of the DEFERRED Angular surface: a second document, cross-frame permission delegation via allow='usb; serial; hid', a bespoke host shell we maintain that is not itself the product, and one more realm hop between the user's click and requestDevice(). Salvaged sub-idea, and it is the decisive one: A's plain dependency-free JS shell with no framework is exactly the right implementation medium — B' keeps A's code and drops A's frame.
- [MERGE] E. KIOSK — installable offline-first PWA with service-worker precache: Split into two halves with opposite verdicts. ACCEPT its vendored-Pyodide half unconditionally: the spike proved that blocking cdn.jsdelivr.net leaves the kernel permanently un-ready, so the current build is not a static site in any meaningful sense, and a lab-automation product plausibly runs on air-gapped machines. Adopt jupyterlite-pyodide-kernel's --pyodide option against a local pyodide dist tarball, accepting the resulting artifact-size increase. ACCEPT the web app manifest plus install affordance as a cheap additive. REJECT the service-worker precache layer for now: JupyterLite already ships its own service worker, stacking a second introduces the worst debugging class in web development, and it is not required once Pyodide is vendored same-origin. REJECT putting the PWA-implies-persistent-storage claim on the critical path: that is an undocumented Chromium heuristic, not a spec guarantee, so persistence correctness must not depend on it.
- [ACCEPT] F. Layered persistence contract — pinned IndexedDB + persist() with surfaced denial + File System Access working folder + explicit export/import: Adopted as the definition of 'savable notebooks', replacing the nominal reading. Four layers each with a stated failure mode: L0 autosave to IndexedDB at the 120s default with contentsStorageName pinned to a fixed literal so path moves cannot orphan work; L1 navigator.storage.persist() requested on first save with DENIAL surfaced as a visible banner rather than a console line; L2 a File System Access working folder granted once, handle kept in IndexedDB, every save mirrored to real disk; L3 one-click .ipynb export and import. L2 is the layer that makes savable literally true, and it is available for free here because the product already requires Chromium for WebSerial/WebUSB, which voids the usual File System Access portability objection. Non-negotiable corollary: if L2 is not active the app must state that work is browser-local and evictable. Today persisted() is false, persist() is never called, and a 'Clear Browser Data' item sits two entries from 'New Folder' in the file-browser context menu — silent eviction of a protocol of record is a data-loss bug, not a UX nit.
- [ACCEPT] G. Build boundary — jupyter lite build in CI producing a versioned tarball; nothing hand-committed; site NOT checked in: Answers design question (4): the standalone page still needs a build step, and pretending otherwise is what produced the current failure. EXECUTED evidence: only 5 of 82 files under assets/jupyterlite/ are git-tracked, .gitignore line 10 excludes the rest, build/ contains a single 2544-byte service-worker.js, lab/index.html references a bundle that does not exist, and serving the tree yields an empty body with a 404 on build/repl/bundle.js. The dead tree IS the checked-in-artifact option, already tried and already failed silently. Adopt: CI runs the build, publishes a versioned tarball to GitHub Releases, the deploy job consumes that exact artifact, and developers fetch the same bytes via a just recipe. Two implementation notes carried from the spikes: invoke the module (python -m jupyterlite_core build), not the jupyter lite console script, because this machine's venv shebangs point at another project's interpreter; and the build must fail loudly rather than emit a partial tree.
- [ACCEPT] H. Loud-failure readiness contract — praxis:ready only after import pylabrobot succeeds; wheel filenames read from a generated manifest, never literals: The wheel-pipeline defect (debt-1289) was proven SILENT and therefore worse than a 404: renaming the wheel produced a 404, micropip's 'File is not a zip file', a swallowed exception, praxis:ready emitted anyway, and a kernel with no pylabrobot at all. Two changes. (1) The bootstrap must assert import pylabrobot after install and emit praxis:error with a visible banner on failure; readiness becomes a claim about the environment, not about reaching the end of a function. (2) The wheel filename must be read from a build-generated manifest.json rather than a string literal, making a stale-name 404 structurally impossible. Retiring Direct Control and the protocol-runner worker collapses the literal from three call sites to one, which is what makes the manifest indirection cheap enough to be obviously right. Also in scope: fix _sync_fetch to distinguish HTTP 200-with-empty-body from failure, since every boot currently logs a false 'praxis/__init__.py: fetch failed' on a 0-byte file and trains operators to ignore the exact channel a real missing shim would use.
- [ACCEPT] I. Storage-identity migration — pin contentsStorageName/settingsStorageName in the SAME release that moves the served path, with a one-time copy from the old baseUrl-derived database: Ordering is load-bearing, which is why this is a decision and not a config detail. EXECUTED proof: same origin, different base paths /siteA/ and /siteB/ produced two mutually invisible databases named 'JupyterLite Storage - /siteA/' and '- /siteB/'. praxis already ships baseHref '/' and '/praxis/', and jupyter-lite.gh-pages.json hardcodes baseUrl '/praxis/assets/jupyterlite/'. The refocus moves the path again, so shipping the move before the pin would silently orphan every existing user notebook — data still on disk, invisible to the app, with no in-app recovery. Verified against the live config: jupyterlite-config.json currently sets only appName, appVersion, collaborative, disabledExtensions, defaultKernel, settingsUrl and themesUrl — none of the three storage-name keys is set. Required: pin contentsStorageName to a fixed literal, pin settingsStorageName likewise, ship a boot-time one-time migration that copies the files store from any legacy baseUrl-derived database name, and only then move the path. Same commit, or the migration is worthless.
- [ACCEPT] Direct Control and the protocol-runner Pyodide worker — retire to the experimental extension rather than carry into web-repl/: Answers design question (5). Convergent evidence, none of it about taste: Direct Control has zero capabilities the notebook lacks, its sole unique affordance being a Material form that emits one line of 'await machine.method(k=v)' that a cell expresses directly; its hardcoded default backend FQN pylabrobot.liquid_handling.backends.simulation.SimulatorBackend raises ModuleNotFoundError against the wheel that actually ships (EXECUTED; chatterbox and STAR import fine), and the '||' default means web_bridge's if-not-fqn guard never fires; it loads Pyodide from cdn.jsdelivr.net, violating the static-site constraint; its machine list and method table come entirely from the deferred SQLite catalog plus a hand-generated 30KB plr-definitions table that drifts every PLR release; and it has had no feature commit since 2026-01-22 while the JupyterLite path received roughly fifteen through 2026-02-14. The protocol-runner worker is retired for a stronger and different reason: its only consumer injects SqliteService, HttpClient, ProtocolsService, environment.apiUrl and a WebSocketSubject, so it is structurally inside the deferred scope. Immediate cheap move, independent of the extraction: delete the unconditional PyodidePoolService.preWarm() at main.ts:26-29, which today boots a deferred-scope Pyodide instance on every single page load. Reversal condition, recorded rather than buried: a stated product requirement for a no-code GUI device surface for non-programmers. That is a product question for the owner, not an architecture question, and it is the only thing that should reopen this.
- [DEFER] INVEST gate — S (Small) criterion: S FAILS as a single story and the tool's automatic gate should not be read as disagreeing — it parsed my verdict block leniently. The winner bundles five separably shippable deliverables and well over eight acceptance criteria. Resolution: this artifact is an AREA DESIGN SPEC that governs a sequence, not a story. Decomposition, in dependency order: W0 fix web_serial_shim.py:24 by dropping 'window' from its js import (WebSerial is unusable in the kernel today) and delete the unconditional preWarm() at main.ts:26-29 — both one-liners, both immediately valuable, both reversible, neither requiring any architecture. W1 build pipeline: web-repl/ skeleton, python -m jupyterlite_core build rather than the broken console script, vendored Pyodide via --pyodide, generated wheel manifest.json, CI tarball to Releases; gated on an offline boot test with cdn.jsdelivr.net blackholed. W2 surface and storage identity: switch repl/ to lab/, pin contentsStorageName and settingsStorageName, ship the legacy-database copy migration in the SAME commit as the path move; gated on a notebook saved at the old path being visible at the new one. W3 praxis-shell.js: build-time injection anchor assertion plus a runtime sentinel that gates praxis:ready, device-auth dialog, loud-failure banner; gated on the real-hardware gesture spike running FIRST, with runner-up A as the fallback if it fails. W4 persistence layers L1 to L3. W5 retire Direct Control and the protocol-runner worker to the experimental extension. All other INVEST criteria pass.

## Pre-mortem Record
**User:** SIX-MONTH PRE-MORTEM. Four plausible failure narratives, ranked by how likely I think they are.

FAILURE 1 (most likely) — "Savable" became a lie again, quietly.
Nobody granted the File System Access working folder. The prompt appeared once on first run, users clicked away because they didn't know what it was for, and the app fell back to L0/L1. Six months later a lab machine ran low on disk, Chromium evicted the best-effort bucket, and a scientist lost three weeks of protocol development. The banner we shipped said "work is browser-local and evictable" — in grey text, in a corner, dismissed on day two. ROOT CAUSE: we treated the FSA grant as an offer rather than a gate. MITIGATION TO SPEC NOW: the first save must be a blocking, explanatory modal — not a passive banner — and the app must display the CURRENT persistence tier permanently in the status area, in a place that is visually alarming when the tier is L0/L1. Also spec a periodic "your work is not on disk" reminder rather than a one-shot.

FAILURE 2 — The injection assertion got loosened.
JupyterLite 0.9 restructured lab/index.html, CI went red, someone on a deadline relaxed the anchor regex to make it pass, the script silently stopped loading, and device auth broke in a way that looked like a hardware problem. Weeks were burned blaming a USB cable. ROOT CAUSE: a build-time assertion protects the build, not the runtime. MITIGATION TO SPEC NOW: add a RUNTIME self-check — praxis-shell.js sets a global sentinel on load, and the bootstrap refuses to emit praxis:ready if the sentinel is absent, emitting praxis:error instead. That converts a silent unshelling into the same loud failure class as the wheel manifest. This is the same lesson as H applied to a second failure mode, and I should have generalised it the first time.

FAILURE 3 — Vendored Pyodide made the artifact unmanageable.
The GitHub Pages deploy grew past a practical size, pushes got slow, and someone "temporarily" reverted to the CDN to unblock a release. Air-gapped support quietly died and nobody noticed because nobody in CI is air-gapped. ROOT CAUSE: we required an offline property with no test that observes it. MITIGATION TO SPEC NOW: a CI check that loads the built site with cdn.jsdelivr.net resolution blackholed and asserts the kernel reaches ready — the spike already demonstrated the exact technique (chromium --host-resolver-rules MAP cdn.jsdelivr.net 127.0.0.1:1) and proved it currently FAILS. Turn that spike into the regression test. Note also the spike's finding that Playwright page.route() does NOT intercept Web Worker requests, so the resolver-rules approach is the only correct one here — that detail must be in the spec or someone will write a test that passes vacuously.

FAILURE 4 — The deferred Angular surface rotted from "alive" to "present in git".
web-repl/ evolved, the BroadcastChannel message shapes drifted, and the Angular playground's iframe kept loading a page whose protocol it no longer spoke. F2 was violated by neglect rather than decision. ROOT CAUSE: "kept alive" was never given an observable definition. MITIGATION TO SPEC NOW: either state explicitly that the Angular embed is expected to break and is not a gate (an honest deferral), or add one smoke check that the embed still reaches praxis:ready. Do not leave it ambiguous — ambiguity here is how F2 gets violated while everyone believes they complied. My recommendation is the honest deferral plus a documented pinned web-repl version the Angular surface embeds, so it breaks at an explicit upgrade rather than continuously.

WHAT I AM NOT MITIGATING, DELIBERATELY: the gesture chain itself. No amount of design removes the need to put a real device on a real machine and click a real button. That is a gated spike, it must run before implementation starts, and if it fails the runner-up A is the fallback. I would rather state that as an open risk than pretend the architecture closed it.
