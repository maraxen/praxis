# Brainstorm: Wheel build, PLR upgrade, and version coherence for the praxis JupyterLite REPL refocus: what mechanism makes drift between the PLR submodule pin, the built browser wheel, the hardcoded TypeScript filenames, and the piplite/wheel index structurally impossible; who builds the wheel and when (local dev vs CI vs committed artifact); and what the Python-version policy should be across venv 3.14.6 / ty 3.12 / package.json pyodide ^0.29.0 / in-browser CPython 3.14.2.

## Problem Frame
FIXED (cannot change):
- The wheel is pure-python `py3-none-any`. No ABI matrix, no per-Python-version wheel variants. One artifact serves all interpreters.
- PLR is consumed as a git submodule at external/pylabrobot; pin is dd79c4c89 (== PyPI 0.2.2). Not relitigable.
- Deploy target is GitHub Pages: static files only, no server-side logic, no custom response headers, no redirects. Anything requiring a header or a server endpoint is out.
- micropip is the only installer in the browser. It fetches a URL. Whatever we do must terminate in "some code computes a URL string and passes it to micropip".
- `jupyter lite build` must run to produce a servable tree — the repo tracks only 5 of 82 files and .gitignore excludes the rest. Nothing boots without it.
- The node toolchain is NOT universally available (absent in the spike environment). The wheel-build step specifically must not require node.
- Two independent Pyodide runtimes consume the wheel: the JupyterLite iframe kernel (via praxis_bootstrap.py, a Python file fetched at runtime) and python.worker.ts + direct-control-kernel.service.ts (TypeScript, compiled by ng build). They do NOT share a module system. Any single-source-of-truth must cross a Python/TypeScript language boundary.

NEGOTIABLE (explicitly on the table):
- Whether the wheel is committed to git at all.
- Whether the filename appears in source at all, versus being discovered at runtime or injected at build time.
- The wheel's filename itself — we control the build invocation, so a local version segment (0.2.2+g<sha>) or a content hash in the name is available.
- Whether Pyodide is vendored into the deploy artifact instead of pulled from jsdelivr.
- Whether ty's target and the venv's Python move.
- Whether the deferred Angular runtimes (python.worker.ts, direct-control-kernel.service.ts) are in scope for the drift mechanism at all, or whether they get deleted/quarantined with the rest of the experimental extension — that reframes the language-boundary problem substantially and I want it examined, not assumed either way.
- CI provider/shape. GitHub Actions is what exists.

FAILURE COST ASYMMETRY (this should drive the design): a drift failure today is SILENT — spike-proven. micropip 404s, the exception is swallowed, `praxis:ready` still fires, and the user gets a REPL with no pylabrobot. So a mechanism that converts silence into a loud failure has value even if it doesn't prevent the drift. Prevention and detection are separately valuable and I want both evaluated, not conflated.

SUCCESS CRITERIA for the winning design: (a) names a detector for each of the four drift scenarios; (b) states who runs the build and whether an offline clone can produce a deployable site; (c) states which artifact each of the four Pythons is authoritative for.

## Idea Pool
- [user] Seven candidates, deliberately spread across the "where does the filename live" axis. Grouped by pole so the orthogonality is visible.
- [user] === PREVENTION POLE (filename lives somewhere that can't drift) ===
- [user] A. RUNTIME MANIFEST. The wheel build emits `assets/wheels/manifest.json` alongside the wheel: {package, filename, version, source_sha, sha256, bytes}. Every consumer fetches the manifest first and derives the URL from it. Filename appears in ZERO source files. Language boundary crossed by data, not by code.
- [user] B. BUILD-TIME CODEGEN. One declarative source (`browser-runtime.toml`) is the truth; a generator emits BOTH `src/app/generated/wheel-manifest.ts` (a typed const) and `assets/python/praxis_wheels.py` (a dict). No runtime fetch — values are baked into the bundle and into the fetched bootstrap. CI runs the generator with `--check` and fails on any diff.
- [user] C. INDEX-DRIVEN RESOLUTION (filename deleted, not relocated). Publish a static PEP 503 "simple" index under `assets/wheels/simple/pylabrobot/index.html` and call `micropip.install("pylabrobot", index_urls=["<root>/assets/wheels/simple/"])`. Source then contains only the PACKAGE NAME. No version, no filename, no manifest fetch. The build regenerates the index as a byproduct of dropping a wheel in the directory. Note this ALSO makes the currently-inert `piplite.packages` config meaningful for the first time.
- [user] D. STABLE-PATH INDIRECTION. Deploy the wheel under a content-addressed or version-stamped path but reference it through an invariantly-named locator — the degenerate case being "the wheels directory contains exactly one .whl and the loader globs for it". Filename lives in the filesystem shape rather than in any file.
- [user] === CONSUMER-ELIMINATION POLE (fewer places to drift) ===
- [user] E. QUARANTINE THE ANGULAR RUNTIMES. Move python.worker.ts and direct-control-kernel.service.ts into the deferred experimental extension in the same commit as the refocus. Then there is exactly ONE consumer — praxis_bootstrap.py — which is a runtime-fetched Python file, not compiled TypeScript. The Python/TS language boundary that forces A/B's complexity CEASES TO EXIST. Drift surface goes 3 sites -> 1.
- [user] === SOURCE-ELIMINATION POLE (no local wheel at all) ===
- [user] F. INSTALL FROM PyPI BY VERSION. dd79c4c89 IS published as PyPI 0.2.2. So `micropip.install("pylabrobot==0.2.2")` needs no local wheel, no build recipe, no filename anywhere. The only key is a PEP 440 version string, which cannot drift from itself. We already have a hard CDN dependency (jsdelivr for Pyodide), so this adds no NEW class of network coupling.
- [user] === DETECTION POLE (accept drift, kill the silence) ===
- [user] G. POSTCONDITION GATE. Make no attempt at prevention. Instead: (1) praxis_bootstrap replaces its swallowing try/except with a hard assertion — `import pylabrobot; assert pylabrobot.__version__ == EXPECTED` — and emits `praxis:error` with a diagnostic payload instead of `praxis:ready` on failure; (2) a Playwright job in CI boots the actually-built static site and asserts the kernel reaches ready WITH pylabrobot at the expected version and the four io shims importable. This is orthogonal to A-F and composes with any of them.
- [user] I'll add one more that spans poles: H. LOCKED BROWSER RUNTIME — a single `browser-runtime.lock.toml` declaring pyodide version, jupyterlite-core/pyodide-kernel pins, PLR sha, wheel sha256, and the websockets wheel; the build reads it and CI asserts the deployed tree matches. This treats the whole browser payload, not just the wheel, as one locked reproducible unit — which is where the jsdelivr and websockets problems also live.

## Decision Log
- [REJECT] D. STABLE-PATH INDIRECTION / glob the wheels directory for the single .whl: Requires directory enumeration from the browser. GitHub Pages does not autoindex a directory that lacks an index.html, and the deploy target is fixed as GH Pages with no server-side logic. The locator is unimplementable. Its surviving fragment — content-addressed naming — is not a locator and folds into idea I (SHA-stamped local version).
- [REJECT] F. INSTALL FROM PyPI BY VERSION — micropip.install("pylabrobot==0.2.2"), no local wheel: Forecloses ever shipping a patched PLR without swapping the whole mechanism — and patching is already in the roadmap (io-layer shims, debt-1290, plus browser fixes upstream has not taken). Also makes the deployed site's contents depend on a third party's availability at every user page load, which is unacceptable for an air-gapped-plausible lab tool. Retained explicitly as the degraded fallback if the local-wheel recipe proves unmaintainable, not as the design.
- [ACCEPT] I. SHA-STAMPED LOCAL VERSION (build from a scratch export of the pinned submodule with version.txt overwritten to 0.2.2+g&lt;sha8&gt;): Upgraded from a filename trick to the load-bearing invariant of the whole design by a read of the 0.2.2 source: pylabrobot/__version__.py reads version.txt from the INSTALLED package at import time, and version.txt is in package-data so it ships inside the wheel. Therefore stamping version.txt makes the source SHA a RUNTIME-OBSERVABLE string — pylabrobot.__version__ == "0.2.2+gdd79c4c8" inside the browser kernel. That single fact gives every drift scenario a detector at the same checkpoint, including "wheel built from main instead of the pin", which was previously undetectable because both refs build to a byte-different but identically-named pylabrobot-0.2.2-py3-none-any.whl. Also invalidates URL-keyed browser/service-worker caches automatically. Does not mutate the real repo: the stamp happens in a scratch git-archive export.
- [ACCEPT] Wheel ownership: DERIVED + GITIGNORED artifact, built by an identical recipe locally (just) and in CI; no committed .whl: The stated committed-vs-CI tension is false for this artifact. The wheel's only input is external/pylabrobot, a submodule already vendored in every clone, so `uv build --wheel` succeeds with zero network. "CI-built" and "offline-buildable" are therefore not in conflict here. The genuine offline blockers are the cdn.jsdelivr.net Pyodide runtime and the newly-mandatory websockets dependency, which are separate problems that were being conflated with this one. Enforcement: gitignore src/assets/wheels/*.whl AND a CI check that no .whl is git-tracked — without the second half the mechanism is a convention, not an invariant, since a hand-copied wheel is exactly how commit 7e29c68 created the original bug.
- [ACCEPT] G. POSTCONDITION GATE — hard version assertion in praxis_bootstrap emitting praxis:error, plus a Playwright boot smoke test in CI: Promoted from optional composable extra to STRUCTURALLY MANDATORY. Any prevention mechanism that adds an indirection (manifest.json fetch, piplite index) adds a new 404 surface that is swallowable by exactly the same broad except-and-continue pattern the spike proved silent for the wheel itself. Prevention without the gate just relocates the silence. Feasibility is now verified rather than assumed: pylabrobot/__init__.py:7 imports __version__, so the assertion target exists at 0.2.2. Assertion is `pylabrobot.__version__ == <stamped expected>`, which under decision I subsumes filename drift, pin drift, wrong-ref drift and stale-cache drift into one check.
- [MERGE] INVEST 'S' (Small): winner as stated spans wheel recipe + manifest seam + runtime gate + CI checks + Python policy + Pyodide vendoring + Angular quarantine: S FAILS as written — well over 8 acceptance criteria and more than one user-facing change. Resolved by splitting rather than overriding. CORE (this spec, ~7 criteria): the wheel recipe with SHA stamp, manifest.json emission, gitignore + no-tracked-wheel CI check, manifest-driven install in praxis_bootstrap, the drift-vs-unavailability postcondition gate, and the Playwright boot test including its negative case. SPLIT OUT as separate tracked items: (a) J, vendor Pyodide / offline capability — different problem, different artifact, gates the 'offline-capable' product claim; (b) E, quarantine python.worker.ts + direct-control-kernel.service.ts — a scope decision owned by the refocus, not by this spec, and the design is explicitly correct with or without it; (c) the ty per-path target override and the package.json pyodide ^0.29.0 reconciliation — cleanup, and (c) partly evaporates if E lands. C' (PipliteAddon index) is a conditional follow-on gated on its own verification spike, not core.

## Pre-mortem Record
**User:** PRE-MORTEM. Six months out, three plausible failure stories, ranked by likelihood.

FAILURE 1 (most likely) — THE GATE GOT TURNED OFF. `praxis:error` fired on a developer's machine for a reason unrelated to drift: a slow CDN, a transient PyPI hiccup, a partially-written manifest during an incremental build. Because the gate is hard-fail with no ready state, the REPL was completely unusable rather than degraded. Someone added a `?skipVersionCheck=1` escape hatch "temporarily", it got baked into the dev Justfile recipe, and within weeks nobody ever ran with the gate on locally — so the gate only ever ran in CI, which is precisely where drift is least likely. The invariant became theatre. MITIGATION the spec must carry: the gate must distinguish DRIFT (manifest says X, runtime says Y — hard fail, no override) from UNAVAILABILITY (manifest 404, network error — fail loudly but with a distinct error code and a diagnostic, so nobody is tempted to blanket-disable the drift check to work around a network flake). One escape hatch, never two, and it must not silence the version mismatch.

FAILURE 2 — THE MANIFEST BECAME A SECOND SOURCE OF TRUTH. The design says manifest.json is emitted by the same recipe that writes the wheel. Six months of small edits later, something else writes it too: a dev regenerates the wheel by hand during debugging, an ng-build step "helpfully" copies a cached manifest, or the deferred-extension branch grows its own writer. Now the manifest can lie, and because the gate compares runtime-version to MANIFEST-version rather than to a pinned expectation, a manifest that agrees with a WRONG wheel passes cleanly. That is the exact silent-success failure we set out to kill, reintroduced one indirection higher. MITIGATION: the gate must anchor on something the manifest cannot fabricate. Cross-check the manifest's `source_sha` against the SUBMODULE pin recorded in git (a CI-side check, since the browser can't see git), and have the manifest record the sha256 of the wheel so the browser can verify the bytes it actually received match the manifest that described them. Manifest-vs-wheel agreement is checkable in-browser; manifest-vs-pin agreement is checkable only in CI. Both are needed and they are different checks.

FAILURE 3 — THE `+local` VERSION SEGMENT WAS REJECTED SOMEWHERE UNEXPECTED. Not by micropip (which we'd have caught in the first spike), but by something downstream we didn't test: piplite's index handling, JupyterLite's kernel-side dependency display, a service-worker cache key that URL-escapes `+` inconsistently, or an ipython/importlib.metadata path that trips on the local segment. The team worked around it by dropping the stamp back to plain `0.2.2` — and with it went the ONE mechanism that distinguished a pin-built wheel from a main-built wheel. The design silently degraded to the pre-existing bug while all the surrounding machinery (manifest, gate, CI check) stayed in place and kept reporting green, because every one of them compares 0.2.2 to 0.2.2. MITIGATION: make the SHA appear in a SECOND, independent place that does not depend on PEP 440 tolerance — specifically, have the build write the source SHA into a file inside the wheel that is not the version (e.g. a `pylabrobot-<version>.dist-info`-adjacent marker or a tiny `praxis_build_info.py` module dropped into the scratch export), so the runtime assertion can check the SHA directly even if the version string is forced back to plain 0.2.2. Belt and braces, cheap.

A fourth, quieter one worth naming: THE OFFLINE STORY WAS NEVER FINISHED. Phase J (vendor Pyodide) was sequenced as a follow-on, and follow-ons slip. Six months later the "static webpage" still hard-depends on cdn.jsdelivr.net, and the first real lab that tried it on an air-gapped bench found the kernel never became ready — which, per the spike, is a hang rather than an error. That is a product failure, not a drift failure, but it kills the same product. It should be tracked as a gate on the product claim ("offline-capable") rather than as a nice-to-have, and until it lands the docs must not describe the site as self-contained.
