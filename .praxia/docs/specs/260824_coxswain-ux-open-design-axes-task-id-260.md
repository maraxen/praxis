## Idea Pool
- [ai] N1-A. Static call-type risk tiering: tag each PLR call at schema level with a fixed risk annotation (read-only / reversible / irreversible) baked into the tool schema itself — queries get zero friction, aspirate/dispense/transfer get single-click confirm, discard/dispense-to-waste/tip-eject get two-step. The "distinct gesture" for the irreversible tier is a typed-word confirmation embedded in the chat input (e.g. type "discard" to arm the Confirm button) rather than a special button — stays chat-native, no new widget class.
- [ai] N1-B. Dynamic parameter-scaled risk tiering: risk tier computed at propose-time from the resolved call's actual parameters, not just its verb — e.g. a 5µL transfer is low friction but a full-reservoir transfer, or any call touching more than one plate, escalates tier regardless of verb. More physically accurate (an "irreversible-in-effect" small-volume waste-dispense and a large one aren't equally risky) but adds a tier-computation function per verb and makes the audit question "why did THIS call get high friction" harder to answer than a static table.
- [ai] N1-C. Hold-to-confirm gesture as the "distinct gesture" mechanism for the irreversible tier (press-and-hold a button, or held spacebar, for ~1.5s) instead of a typed word. Physically distinct from a habituated click, no typing required — but motor-impairment-hostile unless paired with an equivalent keyboard/switch-access alternative, which then reintroduces a second code path to keep in sync. Flagged as accessibility-risky against H4's accessibility floor.
- [ai] N1-D. Typed-keyword confirmation mirroring the action's own verb (user types back e.g. "discard tips at C3" into a field before Confirm activates) rather than an arbitrary word. Directly implements the research's "typed keyword, not button" recommendation, fully keyboard-accessible, chat-native — cost is real per-action time and a risk of users developing a rote muscle-memory phrase they stop reading, which is exactly the habituation failure mode the two-step gesture exists to prevent if the phrase becomes too predictable.
- [ai] N2-A. Full inline per-field editing: every parameter in the propose/confirm card (volumes, source/target references, counts) is directly editable in place; edits re-enter the FFT gate at cue 2 (re-resolve any touched symbolic reference) with debounce-on-blur rather than per-keystroke, per H1's responsiveness constraint.
- [ai] N2-B. Constrained inline editing: only scalar/free-form fields (volumes, counts, tip types) are inline-editable; symbolic/reference fields (source well, target plate) are NOT inline-editable — changing "which resource" requires reissuing a new command through the parse layer. Protects Layer 2b grounding from being triggered ad hoc inside an edit box, at the cost of forcing a full reissue for what feels like a small correction ("wrong plate, not wrong volume").
- [ai] N2-C. Diff-and-resubmit editing: an edit doesn't mutate the card in place — it opens a small text box seeded with the natural-language restatement, the user edits the sentence, and the whole thing re-enters the parse adapter as a fresh NL→call translation, diffed against the original for display. Keeps the parse/ground boundary completely clean (no new "edit-aware" code path through grounding) but reintroduces model latency and re-parse risk on every correction, and duplicates work the FFT gate already does.
- [ai] N2-D. No inline editing (baseline/straw-man): any correction means canceling the proposal and reissuing a new command from scratch. Simplest to implement, zero new re-validation code path, but explicitly the "binary corners" failure mode the fresh research argues against, and forces a full re-speak/re-type for a one-parameter typo.
- [ai] N3-A. Adopt the handshake-hash formalization: at propose-time compute a fingerprint over the specific physical/deck state fields the call depends on (tip state, target resource identity/volume, concurrency flag); at confirm-time recompute and compare; any mismatch hard-aborts into a fresh clarify/re-propose cycle rather than silently re-running the old cues.
- [ai] N3-B. Reject formalization, keep the existing "re-run cues 0 and 3 immediately before execution" mechanism as-is: it is already scoped, already cheap (two of four cues, not a new state-diffing subsystem), and covers the two concretely time-sensitive checks (concurrency, preconditions) the design already identified. A hash is a more general drift detector but detects drift the current design doesn't claim to care about yet (e.g. cue-1/cue-2-irrelevant deck changes).
- [ai] N3-C. Hybrid: keep cue 0/3 re-run as the actual mechanism (no new comparison logic), but formalize its result as a small typed "fingerprint" record purely for the audit trail (feeds N6's log format) — gets the auditability/naming benefit of "handshake hash" language without building a new generalized state-diff subsystem nobody asked for yet.
- [ai] N3-D. In-scope auto-repair for benign drift: if confirm-time re-check finds a minor mismatch (e.g. a plate rotated but still in-bounds, still the right resource), silently correct the internal reference and proceed rather than aborting to clarify.

Matches/Conflicts/Omissions categorized feedback applied ONLY to clarification cards (where a candidate set genuinely needs comparison — e.g. two plate carriers, what matched the query vs. what's missing/ambiguous about each), not to every propose/confirm card where there's no candidate set to categorize.

## Pre-mortem Record
**User:** SIX-MONTH PRE-MORTEM. Four plausible failure narratives, ranked by likelihood.

FAILURE 1 (most likely) — The N2-A visible-revalidation-state got skipped under deadline pressure, silently. The forcing-beat requirement ("unvalidated — re-checking" state on touched symbolic fields) wasn't a separate ticket with its own acceptance test — it was a clause inside the N2-A story. ROOT CAUSE: a safety-load-bearing UI state was specified as a clause, not a gated acceptance criterion. MITIGATION TO SPEC NOW: N2-A's INVEST decomposition must carry its own explicit acceptance test ("attempt to confirm while a touched symbolic field shows 're-checking' must be structurally blocked, not just visually discouraged") — block the Confirm action at the code level while re-grounding is in flight, don't rely on the visual cue alone to stop a fast clicker.

ROOT CAUSE: H3's "name a concrete check" was satisfied in the SPEC but not translated into a blocking task with an owner and a date. MITIGATION TO SPEC NOW: the recon check becomes a literal pre-implementation TODO with its own task_id, blocking N4's implementation ticket from being picked up at all until it resolves — not a footnote inside the N4 story.

FAILURE 3 — N7's scoped override quietly widened.
